# TTL 到期与续期设计

## 到期规则

TTL 默认关闭。相对 TTL 对象保存有效 `ttl_days` 和 `expires_at`。
实际内容成功更新后，按“本次更新时间 + 原 ttl_days（N × 24 小时）”续期。
读取、搜索、reindex、写入失败及空 session commit 不续期。

绝对 TTL 对象保存 `expires_at`，不设置相对 `ttl_days`。内容更新不改变
绝对截止时间；用户可显式修改存活对象的期限。不引入默认 30 天续期，
也不把绝对时间折算成续期天数。已过期对象不能通过更新恢复。

`ttl_relative`、`ttl_absolute` 是接口输入，解析为上述有效期限。
这不意味着删除配置状态和并发元数据：当前 Session 元数据仍保存
`ttl_relative` 来表达显式配置 override，`ttl_days` 表达冻结的有效天数。
`received_at` 兼容保留，用于记录相对期限的内容时间基准。
generation 与清理登记用于阻止旧任务误删或延迟写入复活对象。
这些生命周期字段不要求新增公有云向量 schema 字段。

## 默认配置的增量生效

新对象按最近目录、对应范围、库级默认解析；resource 使用独立的范围默认，
不继承库级 TTL。对象显式设置优先。inherit 继续向上解析，disabled 阻断继承。

修改或关闭库级、目录默认配置，不改写已有对象期限，不自动纳管历史无 TTL 对象。
已有相对 TTL 对象更新内容时，继续按自身冻结的天数续期。
显式修改单个存活对象可以首次启用 TTL，也可以调整已有期限。

## Session 边界

Session 默认整体管理 TTL。成功追加消息、完成有实际内容的 commit 后，
按原相对天数续期；同属该 Session 整体期限的旧附件也随之延长。
正式 Session 创建／配置接口仍只接受相对 TTL，本次不增加 Session absolute 参数。

到期后，普通 Session 访问失败，L2 内容隐藏。后台清理整个 messages.jsonl、
归档消息正文、附件及其 L2 向量，不逐条删除 JSONL 消息。
所有 L0/L1 摘要、对应向量及承载目录继续保留并可见。
消息仅在逻辑到期到物理清理之间暂存，不属于永久保存。

保留已有的显式 Session 子文件／子目录保留设置能力。配置后，存活 Session
迁移为逐文件期限，迁移不改变已有截止时间。该模式下更新一个文件不延长兄弟文件，
messages.jsonl 仍是一个整体，不支持逐消息 TTL；修改根默认配置不改写已有子文件期限。

## 清理与验收

读取按最新 expires_at 判断可见性，后台按天级窗口错峰清理。
worker 在对象锁内复核 generation 和截止时间，严格删除，失败保留重试状态。
调度延迟不等于删除或计费完成的 SLA。

本地验收覆盖配置、相对续期、绝对时间固定、读取过滤、严格删除和重试。
平台配置／预设、实际页面和计费用量核销仍需单独联调；存储删除不代表账单已同步。
